## Methodology transparency: two real bugs found and fixed while producing this number

This is the honest final run, but not the first run. In the interest of not hiding the process behind a
clean-looking result:

1. **First run: 23/24 TP, prevention recall 0.958.** Too good - investigation found `isEligibleForPrevention()`
   counted ANY recommended check whose `failureClassesDetected` listed the actual class, including
   `known_pattern_match` (registry confidence 0.5) and `affected_tests` (confidence 0.6) - both
   `applicability: "always"`, so they appear in every commit's recommendedChecks regardless of whether
   any real risk signal fired. A bare registry declaration was being counted as genuine predictive
   evidence. **Fixed**: `isEligibleForPrevention()` now requires the covering check's own registry
   `confidence` to be >= 0.85 (`DEFAULT_MIN_ELIGIBILITY_CONFIDENCE` in `src/preflight/reconciliation.ts`) -
   the same bar this project already uses for its "deterministic" tier. Result dropped to **16/24 TP, 8
   FN, recall 0.667**.
2. **Second correction**: the single historical record with `failureClass: "UNKNOWN"` (taxonomy-level -
   the evidence itself was insufficient to determine any real class, per `fingerprint.ts`'s own
   `classifyFailureFromEvidence`) was being scored as a miss (FN) - no check registry entry could ever
   detect a class nobody could name. **Fixed**: `UNKNOWN` added to `NOT_EVALUABLE_FAILURE_CLASSES`
   alongside `RUNNER_INFRASTRUCTURE`/`FLAKY`, for the same reason those are excluded. Final: **16/24 TP,
   7 FN, 1 NOT_EVALUABLE, recall 0.696** (16/23 evaluable).

Both fixes are permanent (not reverted after this run) and covered by new tests in
`tests/preflight/reconciliation.test.ts`. Neither fix was made to hit a target number - both were made
because the underlying logic was genuinely wrong, discovered by noticing an implausibly high first
result and investigating why, exactly the discipline Part G's own warning asks for.

## What 0.696 actually reflects, honestly

Of the 24 historical failures, all 16 real TPs are `TYPECHECK` or `CONFIGURATION` class - the two
classes this project's DETERMINISTIC-tier checks (`typecheck`, `build`, `dependency_validation`,
`runtime_parity`) can actually claim high-confidence coverage for. **Every `UNIT_TEST` failure in the
dataset (9 of them) is a miss (FN)** - this project has no high-confidence, static, leakage-safe
mechanism for predicting test failures yet (`affected_tests`/`known_pattern_match` exist in the
registry but at confidence 0.6/0.5, below this bar), matching the P0 study's own case studies #4-#6
conclusion that test-failure preventability "cannot yet claim... without the impact-analysis wiring."
This is a real, disclosed gap, not a hidden one - closing it (wiring DiffCI's own real dependency-graph
impact analysis into a genuine test-failure predictor) is the most concrete, evidence-backed
recommendation this replay produces for future work, not something this report claims to have solved.
